# Phase 5 animation notes

Generated by hand (not by a script, unlike the phase 2/4 ledgers) -- there's
no single numeric pass/fail check for "does the robot move correctly," so
this documents what's exact, what's approximated, and what was directly
verified vs. left as a known gap.

## What this phase adds

`scripts/extract-animations.mjs` walks the live `@splinetool/runtime` scene
the same way `extract-scene.mjs` does, but pulls `obj.data.states` (named
target poses) and `obj.data.events` (things that happen on scene "Start", or
continuously for cursor-tracking "LookAt") instead of geometry.
`scripts/generate-animations.mjs` copies the result into
`src/generated/animations-data.json`. `src/generated/animation-runtime.js`
(hand-written) interprets that data at runtime: `initAnimations()` builds a
`TransitionAnimator` per animated body part and a `LookAtController` per
cursor-tracking object, and returns an `update(dt)` called every frame from
`main.js`'s render loop.

Two independent behaviors are reproduced:

- **Arm/hand idle transition** (arm, elbow, forearm, Hand, and the "Hand
  LEFT" container, both sides): on scene start, each joint eases from its
  rest pose to an authored target `State`, then loops a gentle sway.
- **Head / "Top part" cursor tracking**: continuously rotates toward the
  mouse cursor, independent of the transition system above.

The camera also has an authored `Start` transition (the reference's
fly-in intro), but it's only applied in raw-camera mode (`?fit=0`) -- see
"Camera: deliberately not animated by default" below.

## What's exact (directly verified, not just asserted)

The pose math -- decomposing a captured target `State`'s
`position/rotation(degrees)/scale/hiddenMatrix` into the same
position/rotation(radians)/scale convention `extract-scene.mjs` already
uses for rest poses -- was checked by treating an object's own base
`obj.data` as if it were a captured state and confirming
`poseFromStateData(obj.data)` produces byte-identical output to
`effectiveTRS(obj)` (the function every earlier phase already relies on and
that phase 1 verified visually). They matched exactly, including a
mirrored joint with a negative scale component (`Hand`'s
`scale.x = -1.4`), which is the case most likely to break a naive
implementation.

Per-object timing was also confirmed to come straight from the data, not
from a shared/guessed constant: `arm`/`elbow`/`forearm`/`Hand` each have
their *own* move-delay and move-duration (e.g. `arm` settles at t=5s,
`Hand` at t=6s), and the runtime reproduces that -- verified by reading
`arm.rotation` from the live generated scene at t=6s and confirming it
exactly equals the captured target value.

## What's approximated, and why

**The repeating "sway" tween's true target is not in the exported data.**
Every animated joint has two tweens: one names an explicit target `state`
(unambiguous -- ease to it once, after its own delay), the other has
`state: null` and `repeat: -1` (loops forever). A `state: null` tween
genuinely has no target id anywhere in the file to resolve -- confirmed by
comparing every tween's raw `state` field against that object's own
`states` array; the field is really absent, not a lookup bug. There is no
principled way to recover what this tween is meant to interpolate toward
from the exported data alone. `TransitionAnimator` approximates it as a
ping-pong between the rest pose and the captured target pose, using the
sway tween's own duration/delay for pacing -- documented in
`animation-runtime.js` at the point it's applied.

**Consequence, checked honestly, not glossed over:** comparing the
generated scene against the live reference at the same wall-clock time
(t=6s) after this phase's work shows a real difference -- the reference
shows both arms raised outward with open hands, the generated scene shows
one arm flexed toward the chest and the wrench-holding hand rotated
against the hip. The move-to-target phase was independently verified exact
(see above), so this isn't a pose-math bug; the likely explanation is that
the true sway range extends further than the {rest, target} bound this
approximation uses, and Spline doesn't expose the missing endpoint. This is
a real, acknowledged gap, not a claimed fidelity this phase doesn't have.

**Easing.** Spline's numeric `easing` id (4 on every arm/hand tween, 5 on
the camera's second tween) isn't exposed as a name or curve by the live
runtime, and there's no public table for it. Every tween uses one standard
`easeInOutCubic` regardless of its source id -- an approximation, not a
per-id translation.

**LookAt cursor tracking.** `dampingFactor`/`resetSpeed`/`distance`/
`limitDistance`/`plane` are read from the data, but their precise
geometric/timing definitions aren't documented anywhere accessible from the
runtime. The implementation projects the mouse onto a plane at the
target object's depth (a standard "look toward cursor" technique), rotates
the object's local +Z axis (every LookAt object in this scene authored
`axis: "z"`) toward that point filtered by `enabledRotation`, and smooths
with an exponential decay derived from `dampingFactor`/`resetSpeed` --
reproduces the qualitative behavior (smooth follow, reset when the pointer
leaves), not a verified-exact port.

## Camera: deliberately not animated by default

The camera has its own authored `Start` -> `Transition` (matching the
observed fly-in intro), captured the same way as the arm joints. It is
**only** applied when `main.js` is in raw-camera mode (`?fit=0`) -- the same
mode `scripts/verify-render.mjs` already uses to match the reference's
unscripted camera. In the default view, `fitCameraToObject()` (phase 1)
computes a static full-body framing; letting the authored transition also
drive the camera there would mean two systems fighting over camera state
every frame, undoing the deliberate whole-body-visibility fix from phase 1.
This is a scope trade-off, not an oversight: the recording script
(`scripts/record-animation.mjs`) captures the default (auto-fit, camera
static) view specifically so the body motion is fully visible throughout.
